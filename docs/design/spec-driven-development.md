# Design: Spec-Driven Development + Decision Records

Status: **proposal** · Written 2026-07-07 · Targets a future minor (see ROADMAP "2.5").

This doc proposes two coupled additions to shipkit:

1. **Spec-driven development (SDD)** — durable, verified spec artifacts that answer three
   questions before non-trivial work: *what are we building, how should it work, how will we
   know it's done* — with the "done" answer expressed as tests (TDD/BDD-first).
2. **Decision records (DR)** — a rigorous five-part decision format (with a **falsifiability
   clause**) that fills the "narrative of decisions" gap shipkit's own README names, and
   becomes a first-class elder-readable artifact alongside `PROJECT_MAP.md`.

They are proposed together because the second is the spine of the first: every "how should it
work?" answer *is* a decision, so a spec's design is written **as** decision records.

Both live under a single, predictable artifact root — **`.shipkit/`** — so a human always knows
where shipkit-generated docs are, and the elders (`grandfather`/`eve`), MemPalace, and any future
tooling get one canonical place to reference. See §3.0.

---

## 1. Why — the gap this fills

Shipkit already names this gap in three places:

- **README (Episodic memory):** *"`PROJECT_MAP.md` captures **structure** — how a project is
  built today. It does not capture the **narrative of decisions**: 'why did we pick Paddle over
  Stripe?'"*
- **`skills/explain-system`** already emits decisions in ADR format (Context, Decision,
  Trade-offs, Consequences, Confidence, **Revisit-when**) — a weaker cousin of what's proposed.
- **`rules/shipkit.md` (commit discipline)** already demands *"Name alternatives you rejected
  and why … this is the highest-value line for a future reader."*

So this is not a foreign methodology bolted on — it is shipkit's own stated value, made durable
and queryable. The map looks **backward** (what exists, where). SDD looks **forward** (what
we're about to build). Decision records capture the **why** that connects them — and that neither
the map nor raw `git log` can reconstruct honestly.

### Positioning guardrail (read this first)

Shipkit's 2.0 roadmap deliberately **cut** the old `/plan` skill (a PRD→spec→tasks flow) to
reposition from "methodology bundle" to **"the project knowledge layer for Claude Code."** This
design honors that. It does **not** port GitHub Spec Kit's seven `/speckit.*` commands or
re-add a heavy workflow that overlaps Claude Code's native Plan Mode.

Instead: **specs and decisions are a new class of durable, verified, elder-readable artifact**,
reusing the machinery shipkit already has (archivist writes, grandfather/eve read, the registry
indexes, a SHA-stamped hook keeps it fresh). SDD *extends the knowledge layer forward in time.*
The heavy front-half discipline is carried by an always-on **rule** that rides shipkit's existing
trivial-vs-non-trivial split — not by a new command chain.

## 2. The three questions (the user-facing model)

The organizing idea, in plain language, mapped to the industry-standard SDD triad:

| Question | Artifact | Format |
|---|---|---|
| **1. What are we building?** | `spec.md` — requirements | **EARS default, prose escapable** |
| **2. How should it work?** | `design.md` — the approach | **decision records** (§4), cite the spec |
| **3. How will we know it's done?** | acceptance criteria → **tests** | each EARS `shall` → a BDD/TDD test |

Question 3 is where SDD and shipkit's `test-first` rule fuse: the definition of done is not a
checklist, it is a **failing test written before the code**. Each EARS requirement
(`When X, the system shall Y`) converts near-mechanically into a behavior-focused test
(`describe X … it Ys`). SDD sits *above* TDD: the spec defines *what* to test; TDD drives *how*
it's built.

## 3. The spec artifacts

### 3.0 `.shipkit/` — the artifact root

All shipkit-generated knowledge artifacts live under one predictable root at the repo top level:

```
.shipkit/
  specs/<feature-slug>/
    spec.md      # Q1 — EARS requirements + user stories + acceptance criteria
    design.md    # Q2 — the approach, written as decision records (§4)
    tasks.md     # ordered tasks, each citing the requirement it satisfies
  decisions/
    NNNN-<slug>.md  # project-wide decision records (the "why" log)
```

Why a single dotted root:
- **A human knows where to look** — one place for every spec and ADR shipkit created.
- **The elders get a canonical root** — `grandfather`/`eve` reference `.shipkit/` directly instead
  of guessing paths; MemPalace can index it the same way.
- **Dotted (`.shipkit/`, not `shipkit/`)** groups it with `.claude/` as tool-owned, keeps it out of
  the project's own top-level namespace, and reads as "generated by a tool."

`PROJECT_MAP.md` **stays at repo root** (it is the entry-point index a human opens first, and the
freshness hook already looks there) but **links into** `.shipkit/` — pointing to active specs and
recent decisions. The map is the front door; `.shipkit/` is the filing cabinet behind it.

Specs branch and PR with the code they describe. Layout mirrors the de-facto standard (Spec Kit
`specs/<feature>/`, Kiro `.kiro/`), namespaced under `.shipkit/`.

Each file carries a SHA stamp (`> Spec accepted at commit <sha> on <branch>`), exactly like
`PROJECT_MAP.md`, so drift is detectable (§6).

### 3.1 `spec.md` — Q1, EARS default

Requirements use the five EARS patterns so each `shall` maps 1:1 to a test:

| Pattern | Template |
|---|---|
| Ubiquitous | `The <system> shall <response>` |
| State-driven | `While <precondition>, the <system> shall <response>` |
| Event-driven | `When <trigger>, the <system> shall <response>` |
| Optional | `Where <feature>, the <system> shall <response>` |
| Unwanted | `If <trigger>, then the <system> shall <response>` |

**Escapable** (matching shipkit's `test-first`-not-`strict-tdd`-by-default tone): where EARS is
forced or awkward, drop to a user story + explicit acceptance bullets, and say why. Opinionated,
not dogmatic.

### 3.2 `design.md` — Q2, written as decision records

Not loose prose. Every architectural choice in the design is a **decision record** (§4). This is
what gives the design a spine: it stops being "here's the approach" and becomes "here's the
approach, here's what I rejected, and here's what would prove me wrong."

### 3.3 `tasks.md` — ordered, traceable

Each task cites the `spec.md` requirement it satisfies (`→ REQ-3`). Traceability runs
requirement → task → code → test. Prefer writing the test (from the requirement) before the
implementation, per the workflow rule.

## 4. Decision records — the five-part format

The core contribution. A decision record is sharper and more honest than an ADR. **Five parts,
in order:**

1. **Context** — what situation forced a decision? What constraints were in play? (Without this,
   no one can later judge whether the choice was reasonable *for the situation you were in*.)
2. **Alternatives** — the options actually considered. **≥2 real alternatives** — naming them is
   what proves you *decided* rather than *defaulted*.
3. **Case for** — the argument for the chosen option.
4. **Case against** — the honest argument *against your own choice*: the costs, the risks, what
   you're giving up. (The part almost everyone skips. Writing it is what makes the record
   trustworthy.)
5. **Decision + falsifiability clause** — the choice itself, plus a concrete, checkable
   condition that would reverse it: *"I would reverse this if ___."*

### 4.1 Why the falsifiability clause is the whole point

It is the one part ADRs and `git log` never capture, and it creates a capability nothing else in
shipkit has: **decisions become queryable for staleness.** grandfather can answer *"are any past
decisions now falsified?"* by checking each clause's condition against current reality —
*"chose SQLite because <10k users; now at 40k"* → the clause fired, revisit.

**Hard requirement (enforced, verifiable):** the clause must be **concrete and checkable** — a
metric, an event, a threshold (*"if p99 latency exceeds 200ms"*, *"if we exceed 3 external API
consumers"*) — never a vague hedge (*"if it turns out wrong"*). An LLM can produce hollow
falsifiability; the rule forbids it and grandfather flags it. This mirrors the zero-UNCERTAIN
gate `explain-system` already enforces.

### 4.2 Where decision records live

Two homes, by scope:

- **Inline** in a spec's `.shipkit/specs/<feature>/design.md` — decisions scoped to that feature
  (e.g. "billing retry strategy") live with the spec that spawned them.
- **Standalone** as `.shipkit/decisions/NNNN-<slug>.md` — project-wide decisions (e.g. "Paddle over
  Stripe", "monolith over microservices") that aren't tied to one feature. This is the canonical
  durable log the elders read.

The standalone log is the map's counterpart: `PROJECT_MAP.md` is the *what/where*; the decision
log is the *why*. Together they are the full knowledge layer.

## 5. How it reuses existing machinery (minimal new surface)

The design's efficiency comes from reuse. Almost nothing is net-new infrastructure.

### 5.1 Rules (the always-on discipline — this is what makes it "effortless")

- **`rules/spec-driven.md`** (path-scoped to `.shipkit/specs/**` + active on non-trivial feature work) —
  encodes the three questions, EARS-default, and TDD/BDD-first. Rides the existing
  trivial-vs-non-trivial split from `rules/shipkit.md`: **a one-line fix gets no spec; a new
  feature or multi-file change gets the three-question spec.** So Claude never specs a typo.
- **`rules/decisions.md`** (or a section in `rules/shipkit.md`) — when a non-trivial choice is
  made with ≥2 real alternatives, capture it in the five-part form; skip defaults and one-liners.
  States the concrete-falsifiability requirement as law.

Because these are rules, the discipline fires automatically on the right work without the user
memorizing any command. That is the "effortless" property.

### 5.2 Skills (thin — one or two, not seven)

- **`/shipkit:spec <feature>`** — interviews Q1→Q2→Q3, writes the `.shipkit/specs/<feature>/` tree,
  delegates heavy codebase research to `codebase-explorer`, and uses **native Plan Mode as the
  review gate** before tasks. Runs **inline** (it must ask questions — same constraint as
  `/setup`; forked skills can't use AskUserQuestion).
- **`/shipkit:decide`** *(optional)* — interviews the five parts and appends one decision record.
  May be unnecessary: Claude already surfaces alternatives in plan mode, so the rule alone may
  suffice. Ship the rule first; add the skill only if capture proves unreliable without it.

### 5.3 Agents (small edits, big leverage)

- **grandfather / eve** — teach them `.shipkit/specs/` and `.shipkit/decisions/` are first-class sources.
  Enables *"what are we building next?"*, *"why did we pick X?"*, and the novel *"which decisions
  are now falsified?"* Add the mempalace-style triage note: structured decision records are
  preferred over fuzzy MemPalace recall for "why" questions (verified > recalled).
- **archivist** — when mapping, note active specs and recent decisions and **link them from
  `PROJECT_MAP.md`**, so the map points forward and explains itself, not just backward.
- **eve registry** — optional "active specs" / "open decisions" signal per project, for
  portfolio sweeps (*"where did we decide against microservices, and are those reasons still
  true?"*).

### 5.4 Freshness hook (drift — SDD's #1 documented failure mode)

Extend the existing `scripts/check-map-freshness.sh` (one proven mechanism, not a second one) to
also:
- flag a `.shipkit/specs/<feature>/` whose accepted-SHA is behind HEAD on files it governs (code
  drifted from an accepted spec);
- optionally surface **fired falsifiability clauses** at session start (*"1 decision may be
  falsified — review .shipkit/decisions/0007-sqlite.md"*), if cheap to check.

Silent when fresh, always exits 0 — same contract as today.

### 5.5 Relationship to MemPalace

Complementary, not competing. MemPalace recalls *conversations* (fuzzy, verbatim, semantic). The
decision log is the *deliberate, structured, verified* version — fewer entries, higher signal, no
external dependency. Projects without MemPalace get durable "why" answers from the log; projects
with it get both. Decision records partially substitute for the MemPalace add-on for the specific
case of *decisions* (as opposed to general session recall).

## 6. Scope calibration (keeping it from becoming ceremony)

SDD's real failure mode is overhead on small changes; the decision format's is hollow, defaulted
records. Both are governed by the same reflex shipkit already has:

- **Spec only non-trivial work.** New feature, refactor, integration, architectural change → spec.
  Typo, rename, config, one-liner → no spec. The rule says so explicitly.
- **Record only real decisions.** ≥2 genuine alternatives → record. A forced default → skip (or a
  one-line note). No record without a real fork in the road.
- **Falsifiability must be concrete** or the record is rejected — the guard against LLM-generated
  hollow honesty.

Sweet spot (from the research): **greenfield zero-to-one** and **complex features in large
codebases** where contracts must not break. Brownfield: lock what exists, spec only the delta.

## 7. Open decisions (for the author to settle before building)

Written, fittingly, as the start of a decision log:

- **DR-A: Decision-record home** — ✅ *settled:* one artifact root `.shipkit/`; standalone
  project-wide records in `.shipkit/decisions/`, feature-scoped inline in the spec's `design.md`.
  A single dotted root so humans, the elders, and MemPalace share one canonical place to look.
- **DR-B: `/shipkit:decide` — ship it or rely on the rule?** *Lean:* rule first, skill only if
  needed. Falsifiability clause: reverse if capture-via-rule proves unreliable in practice.
- **DR-C: One hook or two?** *Lean:* extend `check-map-freshness.sh`. Reverse if spec/decision
  freshness logic makes the single script hard to keep silent-on-failure.
- **DR-D: EARS strictness** — settled by the user: **default, escapable.** Reverse toward strict
  only if escaped-to-prose requirements measurably fail to produce tests.

---

## 8. Build order (when approved)

1. `rules/spec-driven.md` + `rules/decisions.md` — the always-on discipline (highest value,
   lowest surface).
2. Teach **grandfather/eve/archivist** to read `.shipkit/specs/` and `.shipkit/decisions/`.
3. `/shipkit:spec` skill (inline, interviews, delegates research, native Plan Mode gate).
4. Extend the freshness hook for spec/decision drift.
5. `/shipkit:decide` *only if* step 1 proves insufficient.
6. Docs: GUIDE.md section, README knowledge-layer table row, CHANGELOG, lint passes.

Each step is independently shippable with its own changelog entry — the shipkit release cadence.
